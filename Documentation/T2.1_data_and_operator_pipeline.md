## What I did

### 1. fastMRI landed, extracted, and verified

`knee_singlecoil_val` was downloaded and extracted to
`data/raw/fastmri/singlecoil_val/`. Verification was not "the tar exited 0" — P-08
records a truncated archive that sat recorded as fetched for days because a broken zip
keeps a valid header and only loses its central directory at the end. So every one of

`reconstruction_esc`.

That mattered here: the extraction finished with **99 MB free** on a 215 GB volume, which
is exactly the condition under which a silent truncation would be expected. There was
none.

The split carries `kspace` fully sampled, `reconstruction_esc`, `reconstruction_rss`,
and — the part that turned out to matter most — a de-identified `patient_id`.

### 2. `singlecoil_test` was downloaded, and cannot be used

Checked rather than assumed, because "we have the test split" is the kind of thing that
quietly becomes a plan:

```
keys:  ['ismrmrd_header', 'kspace', 'mask']
attrs: {'acceleration': 8, 'num_low_frequency': 15, ...}
```

Two independent disqualifications. The k-space is **already undersampled** at a fixed
R=8 and ships the mask it was decimated with, so an operator grid cannot be synthesised
from it — the operator is the variable under study and has to be *chosen* and applied to
fully-sampled k-space. And there is no `reconstruction_esc`, so there is no ground truth,
hence no `err_total`, no `err_free`, and no criterion to evaluate. It is the challenge
submission set. fastMRI+ does not annotate it either.

`singlecoil_train` (72.7 GB) was deliberately not downloaded. Nothing needs it: no config
references it, and the project trains nothing (pretrained solvers only, §17). Not
downloading it also removes the D-014 hazard of train and val landing in one recursive
index.

**So `singlecoil_val` is the entire reported MRI substrate.** That is not a footnote — it
sets the ceiling on how thin `calib_group` can be sliced before groups starve, and it is
what makes the next finding load-bearing rather than tidy. Recorded as P-13.

### 3. The split rule was wrong, and the data said so

D-014 fixed the rule as *"split by patient for LoDoPaB, **by volume for fastMRI**, never
by slice"* — on the assumption that a fastMRI volume is a patient.

It is not. Reading `patient_id` from all 199 volumes:

| quantity | value |
|---|---|
| volumes | 199 |
| distinct `patient_id` | **96** |
| patients owning more than one volume | **96 of 96** |

Every patient in the split owns more than one volume, so splitting by filename leaks
**45 of 96 patients (47%)** across the calibration/test boundary. That is precisely the
hazard D-014 was written to prevent, occurring in the modality D-014 declared safe, and
it fails in the direction that flatters our own numbers: a patient seen during
calibration makes the test set easier, so coverage looks better than it is.

`caliber.data.splits` now owns the split. It is a pure function of
`(salt, patient_key)`, which buys four properties that a shuffled list does not:

- **patient-level** — assignment keys on `patient_id`, never a filename or slice
- **operator-independent** (D-022's binding requirement) — there is no operator argument
  to vary, so a coverage difference between R=4 and R=8 cannot be confounded with anatomy
- **identical across runs and machines** — nothing is stored, so nothing can drift
- **stable as data grows** — adding volumes moves nobody, so today's bank stays
  comparable with one built after the substrate grows

`verify_no_patient_straddles` is the assertion, and `split_summary` prints the counts
before a bank is produced. Recorded as D-027; P-06 updated.

### 5. D-024, and the result it moved

Track 1 found that `solvers/reference.py` cast `P_N(texture)` with `.real` before adding
it to the draw. A random 1-D Cartesian mask is not conjugate-symmetric, so `P_N` of a
real image genuinely has an imaginary part, and discarding it put part of the
perturbation back into the *measured* component — so the draws were not data-consistent
and `s_residual` was non-zero as a pure artefact.

Fixed in both reference samplers: the draw stays in the operator's own complex domain and
magnitudes are taken only where something is measured.

**This changed a result, not just a number**, which is the part worth flagging. Measured
before and after, same operators and seeds:

| | `s_free` R=2 | `s_free` R=10 | `s_residual` |
|---|---|---|---|
| before (`.real`) | 0.0827 | 0.0448 | 0.082 / 0.032 |
| after (complex) | 0.0326 | 0.0377 | **0.000000** |

Before, the artefact dominated the score *and was larger at the near operator*, so the
score fell as acceleration rose and a threshold calibrated at R=2 under-covered at R=10.
After, `s_free` rises with acceleration — the physically correct direction, since a larger
null space holds more free content — and naive transfer **over**-covers instead:

| calibration | deployment | coverage | gap |
|---|---|---|---|
| R=2 | R=2 | 0.947 | −0.047 |
| R=2 | R=10 | **1.000** | −0.100 |
| Mondrian | R=10 | 0.914 | −0.014 |

Over-coverage is not the safe side here. Coverage 1.0 means the transferred threshold
flags *every* region, so the flag carries no information — the same vacuity D-020 records
for the absolute label threshold, arrived at by a different route.

What survives: naive transfer is materially miscalibrated under operator shift, and the
group-conditional backbone restores it (0.914 against a nominal 0.90). The test now
asserts the *magnitude* of the gap and the saturation rather than a direction the
synthetic sampler does not produce. Recorded as D-028.

## Honest limitations

**The licensing question is still open, and it is not a formality.** D-017 asks whether
the download source was NYU's own approved links. The NYU Data Sharing Agreement forbids
third-party redistribution, and if the files came through a mirror or a staged Kaggle
account, **no result off this data is reportable** no matter how well the pipeline runs —
M4Raw would remain the only lawful MRI substrate. Nothing in this week's verification
answers that; it needs a human confirmation, not a check I can run.

**No real solver has touched this data.** T2.2 is still stubbed — DPS, DDNM and FlowDPS
all raise `NotImplementedError`. Every number above comes from the reference sampler,
which D-018 marks non-reportable by construction. The direction of the coverage failure
under a *real* pretrained prior is unknown and must be measured in Week 4, not inferred
from D-028.

**The README smoke table and D-020's coverage figures are stale.** They were produced
under the `.real` bug. They should not be cited until regenerated.

**LoDoPaB still splits by slice.** P-06 is only half closed. `LoDoPaBDataset` does not
read the patient CSVs yet, so the D-014 hazard is live for CT until Week 7.

**96 patients is a small calibration population.** It caps group granularity, and D-021
deliberately keeps noise out of the group axes for exactly this reason. If T1.4's protocol
varies noise as a studied axis, groups will starve.

**The disk is full** (99 MB free), so no score bank can currently be written. P-14 lists
what is reclaimable; nothing was deleted unilaterally because the fastMRI links are
time-limited.

**`free_content` is recorded but unused.** It is the denominator Track 1 asked for; the
criterion that consumes it is a Week 2 Track 1 decision, and τ is set only after a real
prior lands.

## How to run it

Every command below was executed before committing.

```bash
# Land the data (the tar is ~16 GB; the extraction needs ~19.4 GB more)
tar -xf data/knee_singlecoil_val.tar -C data/raw/fastmri

# Verify it, rather than trusting that tar exited 0 (P-08)
python -c "
import h5py, glob
fs = sorted(glob.glob('data/raw/fastmri/singlecoil_val/*.h5'))
for f in fs:
    with h5py.File(f) as h:
        h['kspace'][h['kspace'].shape[0]//2]; h['reconstruction_esc'][-1]
print(len(fs), 'volumes readable')"

# Inspect the split before producing any bank
python -c "
from caliber.data import FastMRIDataset, split_summary
ds = FastMRIDataset(root='data/raw/fastmri/singlecoil_val', split='auto',
                    image_shape=(256,256),
                    annotations_csv='data/annotations/fastmri_plus/knee.csv')
for k, v in split_summary(ds.patient_index()).items():
    print(f'{k:22}', v)"

# Tests and lint
python -m pytest -q          # 114 passed
python -m ruff check src tests
```
